# 项目进展怎样主动更新

阅读[当前核心进展总览](INDEX.md)。每个项目只保留一个`progress/<精确仓库名>.md`，首先写最初科学问题，再用白话说明进展、服务器工作、核验程度和实际执行阶段。原始证据、唯一任务仍在来源项目；项目生死状态仍只在`PROJECT_STATUS.md`，本目录不是另一套任务单或运行状态机。

## 谁在什么时刻更新

| 已发生的事件 | 当场更新者 | 要写清什么 |
| --- | --- | --- |
| 科学议题改变、正式下发或修订任务 | 做决定的B或C | 核心问题的现有证据、为何还需训练、已下发内容；只写已下发，不猜SERVER已启动 |
| 实际启动、恢复、暂停或发生影响执行的异常 | 执行该动作的SERVER | 实际任务/臂、观察时间、运行依据及受影响范围；准备好或命令已发出不算实际训练开始 |
| 当前科学任务的执行工作结束 | 收尾的SERVER | 完成项、结果与缺项，注明执行结束待B/C复核；进程退出码不能证明科学成功 |
| 收到“服务器搞完了”、完成科学复核或发现结论需修正 | 负责判断的B或C | 是否充分核验、已查证据、未核部分及理由，原目标/路线/命题分别如何判断，下一步是复用核验还是必要实验 |

这些是发生事实时的发布责任，不是新增审批阶段。动作执行者无需等待用户询问或其他角色轮询；一次事件更新一次即可，没有变化不写流水账。SERVER仍按既定授权连续执行，不等待进展页“通过”。B/C只读核到尚未登记的真实变化可以补写，但注明代记者和观察时间，不能冒充SERVER回执或B/C共识。

没有部署后台观察服务、定时任务或轮询器。主动性来自B/C和SERVER在自己的下发、启动、收尾、复核动作中同时更新；下面的工具只生成和检查总览，不会自动观察服务器或推送。不得把本约定描述成已经接入所有历史脚本的自动回调。

## 写什么才算充分

- 第一小节保留最初科学问题。新路线写在进展中，不能覆盖原问题；占位问题只有取得原始立题证据才能补正。
- 核心进展的首段用一两句话直说解决了什么、还没解决什么；方法解释为具体动作，避免用内部缩写代替解释。
- “服务器当前内容”写实际在做的事，并区分已下发、实际执行中、执行结束待复核、已复核、暂停或未知；附事件/观察时间。不能因RUN为COMPLETE、任务槽为空或没有PID就单独认定完成。
- “核验说明”同时回答上一轮结论是否可信、下一轮问题是否有依据。列可定位证据、影响结论的剩余未知、已有结果为何无法回答新增训练的问题。若无需新增核验，说明已复用哪份未改变的证据及为何足够；“之前查过”“低分所以重训”不算理由。
- 复算、冻结模型检查、合法标签的离线分析能回答的问题先做；达到决策所需即止。输出相关性和GT理想修复不等于训练因果或可实现收益，不偷看盲集。
- 先比较相关公开核心方法、可用代码和内部结果，选择真正针对主要矛盾的方法；不得把删项、阈值、普通增强或补齐论文表格自动当成下一创新任务，也不要求先复现所有别人方法。

## 更新与发布

1. 先把来源项目的任务、结果或修订依据提交推送。实际启动尚无新科研提交时，可链接已推的任务/恢复入口，并在进展页明确这是SERVER何时核实的执行事实；原日志仍留来源项目，不复制进公共库。
2. 拉取本库最新main，读本项目现有页。只修改自己的页；保留其他角色仍有效的核验结论。较早下发记录不能把已启动/已结束覆盖回未启动，冲突回查来源及时间，不盲目以最后写入为准。
3. 运行`python tools/progress.py .`生成总览，再运行`python tools/progress.py . --check`。总览只由页面生成，不重复手工维护另一份事实。
4. 提交本项目页与总览、推送并回读。并发推送被拒时先取回其他项目更新、合并自己的页并重新生成总览，不强推、不覆盖别人的页。同项目冲突按来源事实合并；无法核实写明未知。发布失败报告“来源已更新、进展尚未发布”，不因此重训或中断有效实验。

维护新项目时由B/C在已获授权创建后建立同名页；项目结束先按原规则更新`PROJECT_STATUS.md`，再同步进展页和总览。历史停止维护项目仅从本库已有登记初始化，不进入、修改或运行来源项目。页面旧版本只留Git历史，不另建归档、事件队列或回执目录。

不写秘密、连接信息、绝对路径、完整聊天/日志、数据、权重或未公开稿件。来源链接用普通Markdown描述性文字，阅读模式不显示冗长地址。
