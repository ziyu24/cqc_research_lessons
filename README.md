# CQC 跨项目科学失败教训库

本库回答的不是“某一轮跑没跑过”，而是：一个项目研究了什么科学问题，实际用了什么方法，哪个主张被什么证据否定或限制，以及以后怎样避免重复犯错。详细代码、数据和实验记录仍以来源仓库为准。

## 每个任务开始时怎么读

1. 确认当前 GitHub 仓库的精确名称。
2. 若根目录存在 `<仓库名>.lessons.md`，先完整阅读，再接受聊天交接、历史摘要或旧稿中的科学结论；接手已有任务时尤其如此。
3. 跨项目任务只读实际涉及的文件。文件不存在表示“本轮没有可归纳的实质科研证据”，不表示项目正确或没有失败。
4. 本库与来源项目冲突时，回到文件列出的提交和相对证据路径复核；以新证据修正文档，不把聊天记忆当权威。

## 文件与条目

- 一个有实质科研证据的仓库对应一个根文件：`<GitHub仓库名>.lessons.md`。
- 文件先写“项目研究什么”和“实际采用过的方法”，再写若干中等粒度教训。
- 每条教训固定写：失败命题、失败原因、后续做法、边界、证据。
- 内部任务号、运行器状态、文件缺失和数值调试过程不是可迁移的科学概念，不进入标题，也不单独充当教训。
- `INDEX.md` 覆盖本次审计的全部 GitHub 仓库，并区分实质科研、占位、基础设施、非论文和上游仓库。

## 写入边界

新增或修订前必须逐库检查来源仓库，证据至少包含仓库名、40 位提交号和相对路径。不得记录密码、令牌、私钥、主机连接信息、绝对路径、完整日志、数据集、checkpoint 或未公开稿件。

快速校验：

```text
python tools/validate.py .
python -m unittest -v tests.test_validate
```
